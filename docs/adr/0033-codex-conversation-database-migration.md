# ADR 0033: Codex の会話を格納するスキーマ 7

ステータス: 採択（未実装）

## 文脈

[ADR 0032](0032-codex-import-ui-and-provider-labels.md) で、Codex の会話を既存の GUI で扱う方針を定める。
取り込み方法は [ADR 0034](0034-import-codex-rollouts.md) に分け、本 ADR は保存先と読み取りの契約を定める。
Codex の取り込みは [ADR 0032](0032-codex-import-ui-and-provider-labels.md)、ADR 0033、[ADR 0034](0034-import-codex-rollouts.md) の採択後に実装する。
ChatGPT の実物待ちや後続 ADR の採択を、この3件の採択と実装の条件にしない。

現在のスキーマは 6 である（`src/db.ts` の `MIGRATIONS`）。
`sources.provider` は種類の接頭辞から生成され、`records` は元の行を保持する。
既存の本文、ツール、会話のビューは Claude の3種類を列挙しているため、新しい種類を追加する必要がある。

会話の要約の主キーは `(provider, session_id)` だが、CLI と GUI の本文取得には `session_id` だけで絞る処理がある。
提供元をまたいで同じ ID がある場合も、会話を混ぜずに取得できるようにする。
これらは基準コミット `05e0c0f58827a1f124e68fe495d2cec4683a775a` の `schema/0001-initial.sql`、`schema/0002-search-and-summaries.sql`、`src/chat-log/store.ts`、`gui/src-tauri/src/store.rs` を読んで確認した。

## 実装すること

### 1. スキーマの移行

`schema/0007-codex-conversations.sql` を追加し、`src/db.ts` の移行配列の末尾に登録する。
`PRAGMA user_version` を 7 にする。
既存の表と `records.rowid` は保持し、既存の記録の更新や削除は行わない。
新しい表を増やさず、共通形式へ変換した行を既存の `records` で扱う。

| 種類 | 保存先 | 会話として扱うか |
| --- | --- | --- |
| `codex/rollout` | `records`。元の JSONL の完全な行 | いいえ |
| `codex/conversation` | `records`。閲覧用に変換した JSONL | はい |

提供元は `codex` とする。
元ファイルと変換した JSONL は別のパスにし、同じパスを2種類で列挙しない。
`sources` の既存の一意制約 `(path, generation)` は変えない。

次のビューを作り直し、既存の会話の種類に `codex/conversation` を加える。
既存の Claude 用の条件と列は維持する。

- `record_text_source`
- `record_tool_text_source`
- `session_messages`
- `messages`

`session_summary_source` は引き続き `session_messages` を集計する。
原本の `codex/rollout` は、本文検索、ツール検索、会話の件数に入れない。
新しい提供元では、元の行と変換行を混同しないよう、写し判定の先行レコードの候補を同じ種類の記録に限定する。
`copied_records` と、スキーマ4で `session_messages` に埋め込まれた写し判定の両方に同じ条件を加える。
条件は、提供元が `codex` なら `s2.kind = s.kind` を要求し、それ以外は既存の判定を維持する。
Claude の監査記録と会話記録の関係も変えないため、既存の提供元には種類の一致条件を加えない。

### 2. 索引と要約

移行では、既存の FTS5 表 `record_texts` と `record_tool_texts` を削除したり全件再構築したりしない。
スキーマ 6 では新しい種類は未対応なので、新しい種類の索引は移行後の取り込みで作る。
古い行のツール本文には圧縮の目印があり、SQL だけで再構築すると元の本文を失うためである。
既存の `session_summaries` も保持し、新しい会話は既存の差分更新で追加する。

取り込み順は「変換行の保存、本文とツールの索引、会話の要約、大きな文字列の抜き出し」とする。
[ADR 0031](0031-store-large-strings-as-compressed-payloads.md) の復元規則を維持する。
変換行で SQL が読む値は、最上位、`message` 直下、`message.content[*]` 直下に置く。
圧縮の目印を本文やツールの検索索引に取り込まない。

### 3. 会話の識別

会話を指定する全経路で、`provider` と `session_id` の組を使う。
ID の文字列に提供元を付け足して保存する方法は取らず、既存の ID も変更しない。
GUI の一覧から本文、ページ読み込み、検索結果から本文、書き出しまで、この組を渡す。
検索結果のメッセージ番号、件数、要約も同じ組で計算する。
`get_block` は rowid で一意になる既存の指定方法を維持する。

新しい提供元の並び順は、時刻、変換行の最上位の `sourceOrder`、uuid の順とする。
時刻なしは既存と同じく空文字列として比較する。
`sourceOrder` は元の入力内の順序を表す0以上の整数とし、Codex では物理行番号を使う。
GUI、CLI、検索結果の番号、書き出しでこの順序を共用し、スナップショットのパスの違いで同時刻の順序が変わらないようにする。
既存の提供元の並び順は変更しない。

CLI の `show`、`export` は `--provider` を受け付け、会話 ID の前方一致と組み合わせて候補を絞る。
提供元を省略した場合は、全提供元の `(provider, session_id)` を候補とする。
候補が1組なら実行し、0組なら終了コード1、2組以上なら候補と `--provider` の指定方法を出して終了コード2にする。
同じ ID が2つの提供元にある場合も、2候補として扱う。
`context` と検索結果からの会話取得も、候補の提供元を保持する。

### 4. 版の互換性と復旧

GUI と `chat-log` の必要なスキーマ版を 7 にする。
版6以下を読み取り専用で開いた場合は、取り込みによる移行を促す既存のエラーにする。
移行は既存のトランザクションで行い、途中の失敗ではビューの変更と `user_version` の更新をまとめてロールバックする。

旧バイナリは版7を拒否するとは限らないため、移行後は旧バイナリを使わない。
README に、取り込みを停止し、SQLite のバックアップ機能で別ファイルへ保存してから、新しい CLI と GUI を入れ直し、1回取り込む手順を書く。
WAL を使う稼働中のデータベース本体だけをコピーする方法は案内しない。
戻すときは全書き込みを止め、旧バイナリとバックアップを対で戻す。
移行後に取り込んだ記録はバックアップには無いため、元ログと既存のエクスポートを保持する。

## 実装しないこと

- ChatGPT の種類やビューの追加。[ADR 0035](0035-import-chatgpt-exports.md) で、実物を確認後にスキーマ7からの後続移行を決める。

- 既存の記録、ペイロード、索引の全件変換。
- SQL からのペイロードの復元。
- 元ログの形式の解釈。これは [ADR 0034](0034-import-codex-rollouts.md) で決める。
- 旧 GUI と新 DB の同時利用の保証、自動ダウングレード、自動 VACUUM。

## データ構造

変換行は既存の `type`、`uuid`、`sessionId`、`timestamp`、`cwd`、`message` を持つ JSON とする。
元のメッセージ ID、親の ID、入力の位置は、変換行の `openai` オブジェクトに保存する。
このオブジェクトは出典の確認用であり、SQL の検索条件には使わない。
元の行 は別途保持し、変換行を原本と呼ばない。

重複判定には、提供元、セッション ID、変換行の `uuid` を使う。
同じ論理メッセージの内容が変わった場合は、[ADR 0034](0034-import-codex-rollouts.md) の規則で異なる `uuid` にする。
古い内容を削除せず、異なる版として残す。

## 不変条件

1. **D1 既存データの保持**: 6から7への移行前後で、既存表の全行と rowid、復元した raw、全文検索の結果、会話の件数が一致する。
2. **D2 原本と表示の分離**: 原本だけを取り込んでも本文検索、ツール検索、会話の件数は増えない。
3. **D3 提供元の分離**: 会話取得、件数、番号、書き出しの全レコードは、指定した `(provider, session_id)` に属する。
4. **D4 原子性**: 移行に失敗した場合のビューと版は移行前と同じであり、再試行の成功後は版7になる。
5. **D5 索引の整合性**: 新しい会話の検索結果は変換行の本文に一致し、圧縮の目印を含まない。
6. **D6 写しの除去**: 同じ提供元、種類、セッション、uuid の変換行は、一覧の件数と検索と本文に1回だけ現れる。

| 境界の入力 | 期待する結果 | 不変条件 |
| --- | --- | --- |
| 空の版6、Claude の各種類が1件ある版6 | 行を失わず版7になる | D1 |
| 圧縮済みツール本文、本文の無い行 | 既存の索引と raw の復元結果を保持 | D1、D5 |
| 原本のみ、変換行のみ、両方 | 会話の対象は変換行だけ | D2 |
| 同じ ID が1提供元、2提供元 | 1候補なら取得、2候補ならCLIは曖昧さを報告 | D3 |
| GUI のページ上限と同数、その1件超過 | 次ページも同じ提供元だけ | D3 |
| ビュー再作成途中の失敗、再試行 | 版6に戻り、再試行で7になる | D4 |
| 同じ変換行が1ファイル、2ファイル | 本文と検索の出現は1回 | D6 |
| 元 ID は同じで内容が異なる2版 | 各版を1回ずつ保持 | D6 |

## テスト設計

テスト名に `D1` から `D6` を含め、実装前に失敗を確認する。

- D1: 版6の全表の行、rowid、索引の検索結果、会話要約、復元 raw を採取し、版7への移行後と比較する。新規DBの0から7への移行も確認する。
- D2、D6: 原本と変換行の組み合わせ、同じファイルの再取り込み、別パスの写しを `bun test` で確認する。原本と変換行の uuid が一致しても変換行が消えず、検索と会話の写し判定が一致することを確認する。既存の監査記録と会話記録の写し判定も移行前後で比較する。
- D3: 同じ session_id を Claude Code、claude.ai、Cowork、Codex に置き、GUI の `cargo test` と CLI の `bun test` で本文、件数、ページ、検索番号、書き出しを比較する。
- D3: CLI の前方一致で0候補、1候補、同じ ID の2提供元、別 ID の2候補を確認する。
- D3: 同時刻と時刻なしの入力を複数のスナップショットから取り込み、GUI、CLI、検索結果、書き出しの順序と番号が一致することを確認する。
- D4: 移行途中に失敗を起こし、sqlite_master と user_version を比較する。再試行と、版7を再度開く場合も確認する。
- D5: 1023、1024、1025バイトのツール本文を取り込み、検索と復元の一致を確認する。
- 手動: 本番DBのバックアップで移行を実行し、移行時間、前後の容量、既存の検索結果を記録する。実測前に所要時間の保証を書かない。
- 手動: バックアップから戻す手順と、新しい GUI と CLI で全提供元を閲覧する手順を確認する。

## トレードオフ

共通形式の変換行を持つため、原本と表示用のデータが重複する。
既存の検索と表示を再利用し、原本から変換の誤りを調べられる方を選ぶ。

会話の識別を複合キーにそろえるため、新機能だけでなく既存の GUI と CLI の引数も変わる。
既存の ID を変更せず、提供元をまたぐ衝突を防ぐために必要である。
